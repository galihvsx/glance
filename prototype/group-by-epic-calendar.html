1 · Where the groupBy setting lives (mock recommendation)

Recommendation: calendar-local control, not DisplayPanel / useDisplaySettings

The calendar currently has no groupBy and no display-settings plumbing — its toolbar holds only nav, Month/Week, iCal, and the hint. A Group: None | Epic segmented control sits in that toolbar (same segmented language as Month/Week), persisted per-project in localStorage under glance:calendar-groupby:${slug}:${identifier}, value "none" | "epic" (a narrowing of the shared GroupBy type), default "none", using the same adjust-during-render pattern as the calendar's view setting (glance:calendar-view:…).

Why not useDisplaySettings? (a) The calendar has no field toggles / group headers infrastructure — wiring the full DisplayPanel would drag in list-specific semantics (state/priority groups, showEmptyGroups, quick-add state targets). (b) Sharing the list's per-project display-settings key would couple two different views: changing Group By on the issue list would unexpectedly restructure the calendar, and vice versa. A calendar-local key keeps the swimlane grouping an independent, per-view preference — consistent with how the calendar already keeps its own view key separate.

2 · Rendering model (what the mock shows)

  • Swimlane gutter + render-only bands. The grid gains a 200px gutter column; every week-row's gutter cell stacks one lane section per live epic (+ Ungrouped), in first-appearance order. Each day cell is vertically partitioned into the same fixed-order bands (one per lane). Bands have no droppable of their own — the whole day cell stays the drop target, exactly as today.
  • Multi-appearance: an issue with N live epics renders a chip in every lane's band of its day cell. Mock: GLC-107 on Oct 21 appears in both Auth revamp and Payments v2, with a link glyph (title="Also renders in the … lane") so users can see it's one issue, not two.
  • Archived exclusion: GLC-108's only epic (Legacy SSO) is archived → no lane, lands in Ungrouped on Oct 8.
  • Ungrouped: always last; hidden when empty (week tab shows the collapsed state).
  • Empty epic swimlanes: hidden (an epic with no dated issues in the visible range gets no lane and no band). The calendar has no showEmptyGroups toggle today — mocked as always-hide.
  • Lane headers: epic name + mono count + compact 5-segment progress bar (EPIC_GROUP_ORDER, GROUP_COLORS, done = completed + cancelled) + "Done X of N" caption. The full EpicGroupBreakdown legend is too heavy for a 200px gutter — the mock uses a compact inline bar.
  • Counts: lane count = number of the lane's issues visible in this grid's range; the progress bar derives from the already-loaded issues (states → state.group via the existing statesById map — no extra fetches, same derived-data discipline as C70/C71).
  • Unscheduled strip: same grouping as lane clusters; the strip remains one droppable / one drag source family (see strip tab). Ungrouped cluster last, hidden when empty.
  • Guests: the Group control is a pure view preference — enabled for all; canEdit still gates DnD only (unchanged C26T0 behavior).

3 · What does NOT change

  • DnD wiring: ScheduleDnd, handleDragStart/End, useScheduleMutation, resolveScheduleDrop(issue, overId, fromStrip) / resolveUnscheduleDrop — untouched. overId stays the day key / UNSCHEDULED_STRIP_ID.
  • Data: the three bounded queries (due/start/undated) already return epics: EpicRef[] on every row (C71 epicsAgg) — grouping is client-side via the shared pure groupIssuesByEpic.
  • Quick-add, peek drawer, iCal flow, empty-state copy — untouched.
  • No backend, no migrations, no webhook changes.

4 · Open questions for the coordinator's spec ruling

Rulings needed before implementation

Q1 — Compact bar vs full EpicGroupBreakdown: the mock uses a compact inline 5-segment bar (no legend) in the gutter. Accept, or require byte-identical reuse of the full component (its legend would dominate a 200px gutter)?

Q2 — Hide-empty-swimlanes vs toggle: mock hides empty epic lanes unconditionally. Keep, or add a showEmptyGroups-style control to the calendar?

Q3 — Strip grouping: mock groups the unscheduled strip into lane clusters. Accept, or keep the strip flat (grouping applies to the day grid only)?

Q4 — Multi-appearance marker: mock adds a link glyph on multi-epic chips. Keep the marker, or render plain duplicate chips with no indicator?

Q5 — Setting location: calendar-local Group: None | Epic control + glance:calendar-groupby:… key (recommended), vs wiring the shared useDisplaySettings / DisplayPanel onto the calendar page.
