Group by Epic — Board

Two candidate surfaces below, same data set. Both reuse EpicGroupBreakdown (5 segments, no triage, GROUP_COLORS, done = completed + cancelled), the C72T0 groupByEpic.ts semantics (multi-appearance, archived-exclusion, Ungrouped-last), and the existing board card face (BoardCardBody) untouched.

  • Option A (recommended): columns per live epic — epic name + count + 5-segment progress header, cards keep their state badge; Ungrouped column last; state/priority column paths untouched.
  • Option B (alternative): state columns stay, epics become swimlanes inside each column — epic name + count + slim bar per swimlane.
  • Data: 3 live epics (Auth overhaul 3 issues, Privacy compliance 3, Mobile onboarding 2), archived epic Legacy SSO excluded (its issue GLN-8 falls to Ungrouped), Ungrouped 2. GLN-58 appears in two columns (multi-appearance, marked with a purple ×2 tag that exists in the mock only).

Open questions for the spec ruling

  1. Option A or B? (recommendation: A)
  2. Drop semantics (A): dropping a card into an epic column = attach the issue to that epic (multi-epic aware, mirrors how priority drops re-stamp priority)? Ungrouped column drop = no-op, or detach-from-all (destructive — likely no-op)?
  3. Quick-add (A): column quick-add stamps state_id today; epic columns should additionally attach the new issue to that epic (mirrors the C72T0 review ruling on stateId quick-add landing in Ungrouped until attached)?
  4. Header count inflation: PageHeader total counts memberships (10) not unique issues (9) under multi-appearance — acceptable, or show unique?
  5. Workflow drop-blocked hints (C68T1) are state-column concepts; epic columns would need their own guard story (or none). Decide with the ruling.
